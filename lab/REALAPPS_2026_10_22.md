# Third-party packet software against ham-modem — 2026-10-22

`lab/realapps_test.sh`: everything on the isolated lab network (172.31.73.0/24), no host ports, no host
networking, no kernel modules. The host side binds only the lab bridge's gateway address (172.31.73.1).

- **Direwolf 1.7** (Debian trixie container) as an on-air peer on `tools/audio_hub.py`: digipeater (WIDEn-N with
  TRACE) and custom beacon. Receive: UDP audio (`ADEVICE udp:7355`). Transmit: Direwolf 1.7 can only write to
  ALSA (no stdout output -- checked in audio.c), so a container-only ALSA `file` PCM ("hubout",
  `lab/realapps/asound.conf`) writes raw samples to a FIFO that `lab/realapps/relay.py` paces into the hub.
- **kissutil** (Direwolf's KISS client) in a second container, connected to our TNC's KISS-TCP port.

## Why not kissattach / the kernel AX.25 stack

Containers share the host kernel: loading `ax25`/`mkiss` from a container loads them on the host, and the kernel
AX.25 code (to our understanding) only works in the initial network namespace, so a container would need host
networking plus privileges -- i.e. it would no longer be isolated from El-Modem's lab. Container-friendly paths:
KISS / AGWPE / TNC-2 (ham-modem's own userspace AX.25 stack), and possibly later a TUN interface for IP over AX.25
or an LD_PRELOAD shim that maps AF_AX25 sockets onto AGWPE for specific kernel-socket tools.
