# FX.25 forward error correction — 2026-10-21

`hammodem/fx25.py`: correlation tags + RS(n,k) over GF(2^8) (0x11d, fcr 1), 16/32/64 check bytes, vectorised
tag correlator (<= 8 bit errors), RS decode (Berlekamp-Massey / Chien / Forney), HDLC re-run over the repaired
data. Every demodulator (AFSK slicers, G3RUH, PAM) feeds it the same bits as its HDLC receiver; frames decoded on
both paths are reported once. Transmit: `--fx25 16|32|64`; receive always accepts FX.25.

## Interop bug found: RS shortening convention

First cross-test: each side repaired *its own* damaged FX.25 frames 20/20 but *none* of the other's. Bisected on
Direwolf's actual bit stream: correlation tags matched exactly (tag 0x02, LSB first) and so did the data packing
(flag, then the AX.25 address bytes), but the parity matched no RS variant (bit order, fcr 0/1, parity order).
Direwolf shortens by padding the k data bytes with **trailing** zeros to 255-nroots before encoding (textbook
shortening prepends them). With that change, parity matched on the first try.

Damage-test lesson: `gen_packets` leaves no silence between packets, so a burst-detector that damaged "each
burst" hit Direwolf's files once in total; frames are now located from a clean decode and damaged 0.3 s before
each frame's end, with plain-AX.25 controls that must decode 0.

## Live, lab ConfBridge, 3% simulated RTP loss, 3 stations x 10 frames, CSMA/CD, single runs

| | plain | FX.25 |
|---|---|---|
| afsk1200 (room 7300) | 30/60 (50%) | 58/60 (96.7%) with /32, 31 frames repaired |
| g3ruh9600 (room 7316) | 57/60 (95%) | 55/60 with /32 (2 repairs); 58/60 with /64 (4 repairs) |

Why: one lost 20 ms packet destroys baud x 20 ms / 8 bytes -- 3 at 1200 (any FX.25 fixes it), 24 at 9600 (needs
/64, which fixes 32), 144 at 57.6k (no FX.25 code can). For the fast modes the remedy is different: interleave
the codeword across packets, or an erasure code at the RTP/packet level (RTP gaps are *known* erasures, which RS
can fix at twice the rate of unknown errors). -> next idea.
