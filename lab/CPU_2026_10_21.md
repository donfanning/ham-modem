# Receive CPU optimisation — 2026-10-21

Unprofiled, one core, 10 unique ~210-byte frames per mode, 10 ms input blocks (`scratchpad cpu.py`):

| modem | before | after |
|---|---|---|
| afsk1200 | 4.7% | 2.1% |
| afsk300 | 2.6% | 1.3% |
| g3ruh9600 | 2.5% | 2.5% |
| g3ruh19200 | 4.2% | 3.8% |
| g3ruh38400 | 7.6% | 7.4% |
| pam19200 | 6.2% | 3.9% |
| pam57600 | 14.7% | 7.4% |

Changes:
- AFSK had doubled since FX.25/IL2P: five slicers each ran the vectorised FX.25 correlator on ~12 bits per
  block (pure call overhead) and a per-bit IL2P loop. FX.25 now batches 256 bits before a tag search; IL2P's
  receiver is vectorised (24-bit window sync search, header/payload sliced out once their length is known).
- `HdlcDecoder.push_bits`: a numpy HDLC decoder (flag windows, abort and stuffing from run lengths) proven
  equivalent to the per-bit decoder on 20 randomised streams (noise, aborts, corruption, random chunking:
  identical frames and bad-FCS counts). Used by PAM; AFSK/G3RUH keep the per-bit decoder because their PLLs
  read `hdlc.active` mid-loop. CRC is table-driven.
- PAM's block loop: symbol and half-symbol points interpolated in one pass, Gardner error as one dot product,
  DCD quality computed once per call instead of per block. Decode results unchanged (40/40/39/35/40 across
  clean / 1000 / 1300 / 1600 rms / drift). Larger tracking blocks were tried: 32 saves ~1.3% more CPU but
  loses noise margin (1600 rms: 33 vs 35), 64 saves more but 26 vs 35; kept 16.

Note: identical frames sent back to back are (correctly) collapsed by the duplicate filter -- benchmarks must use
unique frames. Connected-mode retransmissions come after T1 (>= 4 s), far outside the ~0.5 s window.

Live sanity after the changes: pam57600 room 36/36, afsk1200 FX.25/32 room 36/36.
